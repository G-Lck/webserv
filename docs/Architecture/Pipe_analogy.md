# The CGI Bridge: Connecting Python to `send()`

This is the exact moment where static file serving turns into dynamic web hosting! It is crucial that we understand this, because **the Python script does not use `send()`, and it does not talk directly to the browser.** Our C++ server is the middleman. Let's use our Office Building analogy to map out exactly how data flows from a Python `print()` statement out to the client's web browser using `send()`.

---

## The Setup: The Front Desk and the Basement

* **The Client Socket (`newfd`):** The phone line connecting the outside world to our Receptionist.
* **Our C++ Server:** The Receptionist at the front desk.
* **The Python Script:** A specialized worker locked in the basement.
* **The Pipe (`pipefd`):** A pneumatic tube connecting the front desk to the basement.

### Step 1: The Request Arrives
A browser connects to us and sends `GET /cgi-bin/time.py HTTP/1.1`. Our C++ server reads this using `recv()`. The router realizes this matches our `/cgi-bin` location block, so we know we need to execute code instead of just reading a static HTML file.

### Step 2: Building the Tube and Cloning
Our C++ server cannot run Python directly. So, we do two things:
1.  We call `pipe()`. This creates a memory buffer in the OS with two ends (two file descriptors): one for reading, one for writing. Think of this as installing the pneumatic tube.
2.  We call `fork()`. We clone our Receptionist. The Parent stays at the front desk. The Child goes to the basement.

### Step 3: The Python Execution (The Basement)
Down in the basement, the Child process uses `dup2()`. It takes the "Write" end of the pneumatic tube and forces it to become Standard Output (`STDOUT`, fd 1). 

Then, the Child calls `execve("/usr/bin/python3", "time.py")`. The Child transforms into the Python interpreter. 

When the Python script runs a command like `print("<h1>The time is 12:00</h1>")`, Python *thinks* it is printing to the terminal screen. But because we used `dup2()`, that text gets sucked directly into the pneumatic tube!

### Step 4: Reading the Output (The Front Desk)
Back at the front desk, our C++ Parent process is monitoring the "Read" end of the pneumatic tube using our `poll()` loop. 

When `poll()` tells us there is data in the tube, we use the standard `read()` function to pull the text out: `"<h1>The time is 12:00</h1>"`. 

### Step 5: The Delivery (`send()`)
Now, our C++ server has the HTML generated by Python saved in a `std::string` buffer. But we can't just send that raw text to the browser; the browser needs a valid HTTP response!

Our C++ server prepends the necessary HTTP headers:
```http
HTTP/1.1 200 OK

Content-Type: text/html

Content-Length: 26



<h1>The time is 12:00</h1>
```

**FINALLY**, our C++ server takes this complete package and calls **`send(client_socket, response_buffer, ...)`**. 

---

## Visualizing the File Descriptor Flow

Here is exactly how the data moves between the different file descriptors (FDs) in the OS:

| Actor | Action | File Descriptor Used | The Data |
| :--- | :--- | :--- | :--- |
| **Python Script** | `print()` | `STDOUT` (Redirected to Pipe Write FD) | `"<h1>Hello</h1>"` |
| *(The OS Memory)* | *Buffers data* | *The Pipe* | `"<h1>Hello</h1>"` |
| **C++ Server** | `read()` | Pipe Read FD | `"<h1>Hello</h1>"` (Saved in C++ string) |
| **C++ Server** | String Concatenation | None (in RAM) | Adds `HTTP/1.1 200 OK...` |
| **C++ Server** | `send()` | **Client Socket FD** | Pushes the full HTTP package over TCP. |

## Summary of our Rule
**`send()` is strictly for writing to network sockets.** We never give the Python script access to the client socket. We use pipes to bring Python's output into our C++ program, package it as HTTP, and then we `send()` it ourselves.
