# MULTIPLEXING

## Handling Multiple Clients (Conceptually)

To handle multiple clients without freezing, we have to completely change how the server interacts with the operating system. We move from a **Blocking** architecture to **I/O Multiplexing**.

Here is how the concepts map out:

| Concept | The "Blocking" Way (Ex.1 example) | The "Multiplexing" Way (Ex.2 (Webserv Standard)) |
| :--- | :--- | :--- |
| **The Analogy** | A waiter takes an order from Table 1, walks to the kitchen, and stares at the chef until the food is ready. Table 2 and Table 3 cannot even ask for water. | A manager watches all the tables. The manager only taps the waiter on the shoulder when a table is *ready* to order or when the kitchen *finishes* a meal. |
| **The OS Tool** | Functions like `accept()` and `recv()` pause the entire program until data arrives. | We use an OS monitor (like `poll()`, `select()`, or `epoll()`). We give it a list of our open connections and say: "Wake me up only when one of these is ready to talk." |
| **Socket Behavior** | Sockets default to blocking mode. | We explicitly set our sockets to **Non-Blocking** using a function called `fcntl()`. If we try to read a non-blocking socket and it has no data, it immediately returns an error saying "try again later" instead of freezing the program. |
| **The Main Loop** | `Wait for 1 connection -> Read from it -> Send to it -> Close it -> Repeat.` | `Ask OS who is ready -> Loop through the ready list -> If it's a new person, accept them. If it's an old person, read/write to them -> Repeat.` |

By giving a list of file descriptors to a monitor like `poll()`, the OS does the waiting for us in the background, letting our single-threaded C++ program instantly jump to whatever client actually needs attention.

## How to Handle Multiple Clients

Right now, your server is completely linear. It stops and waits at `accept()` until a user connects. Then, it stops and waits at `recv()` until that user sends data.

If a user connects but has a terrible internet connection and takes 30 seconds to send their HTTP request, your entire program is frozen at `recv()`. No one else can connect. No one else can get their webpages. This is called **Blocking I/O**.

To fix this for WebServ, you will use **I/O Multiplexing** (usually using a function like `poll()`, `select()`, or `epoll()`). Here is the exact logic of how you will build your server without freezing:

### 1. The Roster (The Master List)
Instead of just dealing with one socket at a time, you will keep a list (like an array or a vector) of every single file descriptor you care about. At the very start, this list only has one item: your main `socketfd` (the one that listens for new people).

### 2. The Monitor
Instead of calling `accept()` or `recv()` directly, you hand your entire roster over to the operating system using a multiplexing function (like `poll()`). You tell the OS: *"Put my program to sleep. Do not wake me up unless someone on this roster has something to say."*

### 3. The Wake-Up Call
The OS watches the hardware in the background. When something happens, it wakes your program up and highlights exactly which file descriptors on your roster are "ready."

### 4. The Two Scenarios
You loop through the highlighted file descriptors and act based on *who* triggered the wake-up:

* **Scenario A: The main listener (`socketfd`) is highlighted.**
  This means a brand-new browser is trying to connect. You call `accept()`. Because you know the client is already waiting, `accept()` happens instantly. You take the `newfd` generated by `accept` and **add it to your roster**.
* **Scenario B: A client connection (`newfd`) is highlighted.**
  This means an existing user has finally sent their HTTP request (or disconnected). You call `recv()`. Because the OS promised you there is data waiting, `recv()` grabs the data instantly without freezing your program. You process the request, send the response, and if the connection is done, you close the fd and **remove it from your roster**.

### 5. The Loop
Once you process everyone who was highlighted, you hand the updated roster back to the OS, go back to sleep, and wait for the next event.

By doing this, your server only ever interacts with sockets that are 100% guaranteed to be ready, meaning your code never gets stuck waiting on a slow client.

## The Multiplexing Recipe: Step-by-Step

### 1. Setting up the Main Listener
Before we can multiplex, we need a standard server socket to listen for incoming connections.
* **`socket()`**: Creates the main file descriptor.
* **`setsockopt()`**: Configures socket behavior (e.g., `SO_REUSEADDR` to reuse the port immediately after a restart).
* **`bind()`**: Attaches the socket to a specific IP address and Port.
* **`listen()`**: Tells the OS to start queuing incoming connection attempts.

### 2. Going Non-Blocking
This is the most critical rule of multiplexing. A multiplexed server must never get stuck waiting.
* **`fcntl(fd, F_SETFL, O_NONBLOCK)`**: You must apply this to your main listening socket AND every new client socket you accept. It forces functions like `recv()` and `accept()` to return an error immediately if there is no data, rather than freezing the program.

### 3. Creating the Roster (`struct pollfd`)
The `poll()` function requires a specific structure called `pollfd` to track who we are watching and what we are watching them for.
* **`fd`**: The file descriptor you want the OS to watch.
* **`events`**: What you are waiting for (e.g., `POLLIN` means "tell me when this fd has data to read").
* **`revents`**: The "returned events." The OS fills this in to tell you what actually happened.

*At the start, you create an array (or `std::vector`) of `pollfd`s and put ONLY your main listening socket inside it.*

### 4. The Infinite Loop & The Monitor
You enter a `while(1)` loop. This is the heartbeat of your server.
* **`poll(struct pollfd *fds, nfds_t nfds, int timeout)`**: You hand your array of `pollfd`s to the OS. The program pauses here. The OS monitors the hardware and only wakes your program up when one or more FDs in your array trigger an event (like receiving a message or a new connection).

### 5. Iterating Through the Results
Once `poll()` wakes up, you loop through your entire `pollfd` array and check the `revents` field of every single item. 
* If `revents` is `0`, nothing happened on that socket. 
* If `revents & POLLIN` is true, that socket is ready to be read.

### 6. Scenario A: The Main Socket is Ready
If the socket that triggered `POLLIN` is your main listening socket, it means a new browser is trying to connect.
* **`accept()`**: You accept the connection to get the `newfd`. (It happens instantly because `poll` confirmed they are waiting).
* **`fcntl()`**: You immediately set this new client socket to `O_NONBLOCK`.
* **Add to Roster**: You create a new `pollfd` struct for this client, set its `events` to `POLLIN`, and append it to your array.

### 7. Scenario B: A Client Socket is Ready
If the socket that triggered `POLLIN` is an existing client, it means they sent their HTTP request (or they disconnected).
* **`recv()`**: You read the data. Because `poll()` guaranteed data is there, this happens instantly.
* If `recv()` returns `0`, the client disconnected.
* If `recv()` returns `> 0`, you store the data and parse the HTTP request.

### 8. Sending the Response
Once you have fully read and parsed the HTTP request, you must send a webpage back. You change the client's `events` flag in your array from `POLLIN` to `POLLOUT`.
* **`POLLOUT`**: Tells `poll()` to wake you up when the client's network connection is ready to *receive* data without blocking.
* **`send()`**: When `poll()` wakes up for `POLLOUT`, you push your HTTP response to the client.

### 9. Cleanup
When the transaction is completely finished, or if the client disconnected:
* **`close()`**: Close the client's file descriptor to free up system resources.
* **Remove from Roster**: Delete that client's `pollfd` from your array so `poll()` stops watching it.
